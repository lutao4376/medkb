# 医疗器械上市公司财报问答知识库

作业三 · A 案。12 家 A 股医疗器械公司 × 4 份定期报告 = **48 份 PDF**，从抓取一直到
带引用的问答页面全流程自建，检索用 **BM25 + 向量 + RRF 融合**。

---

## 1. 语料

| 项 | 值 |
|---|---|
| 公司 | 12 家（迈瑞、联影、鱼跃、乐普、安图、南微、大博、惠泰、开立、爱博、心脉、澳华） |
| 报告 | 每家 4 份：2024 年报、2025 半年报、2025 年报、2026 半年报 |
| 来源 | 巨潮资讯网（cninfo.com.cn），沪市深市一份源全覆盖 |
| 体量 | 48 份 PDF / 134.9 MB → 解析出 1733 万字 |
| 分块 | 32,239 块，其中表格块 35%，长度中位数 644 字，均值 440 token |

选巨潮而不是只抓上交所，是因为 12 家里沪市深市都有；`column=sse|szse` 一个接口全覆盖。

## 3. 检索设计

四层，每一层都是**先测出来、再定下来**的，不是拍脑袋：

### 3.1 BM25 索引正文，不索引表头

`embed_text` 是"公司名 + 章节 + 页码 + 正文"，看着信息更全，但公司全称在**每一块**里
都出现，df 被拉到接近 1，idf 失效。实测问"迈瑞医疗 2025 年的营业收入"，排第一的是
**2024 年报的封面页**——因为整页都在重复公司全称。

换成只索引正文后，正确的 2025 年报那页排到第一。对比脚本：`src/bench_bm25_field.py`。

### 3.2 公司名当过滤器，不当检索词

只索引正文会带来副作用：财报表格里通常**不重复公司全称**（只在上方的页眉出现），
所以"迈瑞医疗"这个词匹配不到数据表。实测点名迈瑞的题，**top-8 里有 5 块来自别的公司**。

解法是把公司名当元数据过滤（`Searcher.search` 里识别题面点名的公司后走 `only`），
而不是当检索词。同时要**解掉 `per_company` 限流**——它本来是防止全景题被一家公司
霸榜的，定向到单公司后反而把该公司的表挤到 8 块之外。

### 3.3 按题面推报告期

语料里"年度"和"半年度"报告的**章节名完全一样**（都有"主要会计数据"），词面分不开。
后果很严重：问"2025 年营业收入"，检索到的是 **2025 年半年报**，模型据此断言
"全年未披露"——**答错还很自信**。

从题面推报告期（提到半年/中报 → 半年度；提到年报/年度/全年，或只提年份 → 年度），
做成元数据过滤。实测报告期纯度从 **25%~75% 提到 100%**，全库数值覆盖
**5.6% → 14.6%**（`src/eval_retrieval.py`）。

**光按报告期过滤还不够，年份也得过滤。** 语料里同时有 2024 年报和 2025 年报，
两者 `kind` 都是"年度"——所以问"2025 年营业收入"，照样会捞到 2024 年报的块当 2025 的数用。
题面只提一个年份时就按年份过滤（提了两个年份说明要对比，那就不过滤）。

### 3.4 全景题：逐家扇出

问"12 家里谁营收最高""谁净利润在下滑"这类题，单轮 top-k **无论怎么排都只有 8 块**——
12 家的数塞不进 8 块里。这不是排序排偏了，是候选池的容量问题，调分数、调权重都没用。
所以加了一个 `panorama` 模式：**逐家问一次，每家取 k 块，轮转合并**，把"每家必须有"
变成硬约束。合并用轮转而不是按分数排，因为按分数排又会退化成"迈瑞的块排前面、后 4 家被截断"。

### 3.5 RRF 融合

BM25 分数无上界、向量是余弦，量纲没法比，所以用 RRF（`k=60`）只看名次：

```
score(d) = Σ_r 1 / (RRF_K + rank_r(d))
```

### 3.6 消融：每一层到底值多少分

`python src/bench_retrieval_ablation.py --with-vec` 现算，不调模型。**按 topk 分组，
同组才可比**（理由见下）：

| 配置 | mode | topk | 数值覆盖 |
|---|---|---|---|
| 无元数据过滤 | bm25 | 8 | 5/89 = 5.6% |
| + 报告期过滤 | bm25 | 8 | 13/89 = 14.6% |
| + 年份过滤 | bm25 | 8 | 15/89 = 16.9% |
| 年份过滤（只用向量） | vec | 8 | 13/89 = 14.6% |
| 年份过滤（混合） | mix | 8 | 20/89 = 22.5% |
| 年份过滤（纯 BM25） | bm25 | 24 | 32/89 = 36.0% |
| 年份过滤（只用向量） | vec | 24 | 20/89 = 22.5% |
| 年份过滤（混合） | mix | 24 | 34/89 = 38.2% |
| 年份过滤（**全景扇出**） | panorama | 24 | **53/89 = 59.6%** |
| 年份过滤（纯 BM25） | bm25 | 48 | 42/89 = 47.2% |
| 年份过滤（混合） | mix | 48 | 35/89 = 39.3% |

三处读数：

1. **元数据过滤是性价比最高的一层**：什么都不动、只按题面推报告期和年份，
   topk=8 下覆盖率就从 5.6% 抬到 16.9%（三倍）。
2. **小预算下混合赢，且赢过两路单打**：topk=8 时 mix 22.5% > bm25 16.9% > vec 14.6%。
   这正是 RRF 该有的样子——只看名次，两路互补。
3. **但混合的优势是"小预算优势"，不是普遍优势**：预算加到 48，纯 BM25 反而到 47.2%，
   超过混合的 39.3%。同预算 24 下，扇出 59.6% 大幅领先混合 38.2%。

**这张表要说实话，包括对我自己不利的部分，也包括我改过的错。**
我最早手测扇出那一行得到 **40/89**，并据此在 README 里写下"把预算加到 48 块，
纯检索就能反超扇出"。那个 40/89 是**错的**：当时我用 `Searcher(need_vec=False)`
图省事不加载 132MB 向量，而 `panorama` 的底是 `mix`——向量一缺，`mix` 就
**静默退化成纯 BM25**，量出来的其实是"扇出 + 纯 BM25"。补测（`need_vec=True/False`
各跑一遍）复现了这个差：

| | panorama | bm25 | mix |
|---|---|---|---|
| 向量已加载 | **53/89** | 32/89 | 34/89 |
| 向量缺失 | **40/89** | 32/89 | 32/89 |

向量一缺 `mix` 就塌成 `bm25`（34→32，与 bm25 的 32 完全一致），扇出跟着从 53 掉到 40。
**所以"纯检索加到 48 反超扇出"这句话不成立**——48 块的 bm25 是 47.2%，仍低于扇出的 59.6%。
教训是：`mix` 在向量缺失时**不报错、静默降级**，这种"看起来跑通了"的失败最容易骗到自己，
现在 `Searcher` 会记住向量是否真的载入。

数值覆盖这个口径本身也要当心：它是"值有没有出现在召回块拼起来的文本里"，
**块越多拼得越长、命中越容易**——所以不同 topk 之间不能直接比。
另外这个口径下 `topk=48` 并不等于 48 块：多公司题受 `per_company=3` 约束，
实测只回 29~36 块（单公司题因为 `only=` 把上限放开到 `10**9`，才真能回满 48 块）。

## 4. 逐题评测

```bash
python src/answer_key2.py --write                                # 真值：从年报表里抠
python src/make_questions.py --write                             # 题面真值：从上面那份现算
python src/bench_retrieval_ablation.py --with-vec                # 消融表，不调模型
python src/qa.py --questions data/questions.json --mode mix      # 调模型，10 题约 6 分钟
python src/score.py --runs out/qa_bm25.json out/qa_mix.json out/qa_pano.json \
  --md out/检索评测.md
```

三个 mode 一起跑就是 `bash tools/run_eval.sh`（消融 → 纯检索评测 → 3 次调模型 → 判分，
约 25 分钟；`qa.py` 每题调一次模型、约 35 秒，`panorama` 因为要逐家扇出更慢）。

交付物：

```bash
python src/app.py --port 8760 &    # 起页面
bash tools/shots.sh                # 截 9 张图 -> docs/shots/
python tools/md2pdf.py docs/一页结论.md   # -> docs/一页结论.pdf
```

`score.py` 的逐题表里有一列叫**「卡在哪」**——作业要的"失败原因"在这里：
`检索未覆盖` / `部分覆盖（n/m）` / `引用越界` / `数值全中`。区分这几类是因为
它们该改的东西完全不同：前两类要改检索，引用越界只要修输出格式，
不分清楚就会对着模型调半天，其实问题在召回。

统计口径要说明：10 题里 Q6（语义检索）、Q10（跨表推理）**没有数值基准**
（它们问的是"有没有提到、怎么描述的"，不是数字），所以它们的「卡在哪」是
`无数值基准`。算「数值全中」时分母只算**有基准的 8 题**。
最初那版汇总行拿 `n_miss == 0` 当"全中"，把这两题也算进去了——
分母虚高的 5/10 和真实的 3/8 差得不是一点，已经改掉。

`eval_retrieval.py` 是关键工具：**不调模型**，只问"该找到的数字，在被召回的块里
找得到吗"。LLM 一次回答 35 秒，改一个检索参数重跑一遍根本没法调；这一层几秒出结果。

判分基准（`data/answer_key.json`）不是手写的，是从各家公司年报第二节的
"主要会计数据"表里抠出来的，并与第三节正文的叙述句**逐家交叉核对**；
题面里的真值再由 `make_questions.py` 从这份基准现算。数字只有一个来源。

> **踩过的坑**：第一版基准用"找锚点标签 → 往后扫"的方式取数，被第 9 页的
> **「分季度主要财务数据」**截胡——那张表也有"归属于上市公司股东的净利润"这个标签，
> 扫到的第一个数 `92,558,116.80` 是爱博 **2025 年一季度**的数，被当成全年数写进了基准
> （真值 `268,170,112.64`）。连带 Q8 的真值也跟着错成 -23.14%。
> 锚点扫法对"同名标签在附近出现多次"完全没有抵抗力；现在改成只认
> 「第二节 + 2025年/2024年 两列」那张表。详见 `src/answer_key2.py` 的文件头。

## 5. 主要发现

**① 表格的"词汇鸿沟"是真的，但它**没有代价**——而我在这一点上连着错了两次。**

问联影的同比增长率，含**全部四个原始数字**的块是 `联影医疗 2025年年度报告 第14页`，
它本身是完美的，却**一个查询关键词都不含**：增长率在表里是裸数字 `33.98`，
列头是"本期比上年同**\n**期增减(%)"——被 PDF 折行切断，"同比"这个词根本不存在。
于是 BM25 把正文里写着"同比增长"的段落排到前面。

名次是可量的，而且**每一层过滤都把它往上抬**：

| 配置 | 候选池 | 该块 BM25 名次 |
|---|---|---|
| 完全不过滤 | 32,239 | 655 |
| + 报告期=年度 | 18,367 | 415 |
| + 年份=2025 | 8,790 | 215 |
| + 公司=联影医疗 | 981 | **22** |

**第一次错**：我只测了第一行，就写下"检索只取前 50 条候选，它从来没进过候选池"。
加上元数据过滤后池子缩到 981 块，它进得来——名次 22。那句话只在已废弃的配置下成立。

**第二次错（更严重）**：我接着写"名次 22 在 top-8 之外，**所以只用 BM25 这题答不出**，
混合检索才能答出"。三路名次确实是 bm25#22 / vec#2 / mix#4，看着像一条完美的证据链。
但**调模型实测，三个 mode 的 Q2 全是「数值全中 2/2」**（33.98% / 48.14%），
`out/检索评测.md` 里写得清清楚楚。原因是我只查了"那个块在不在 top-8"，
没查"这个事实还有没有别处写着"——p.15 第二节正文里就有一句：

> 公司2025 年度实现营业总收入1,380,025.17 万元，**同比增长33.98%**；实现归属于母公司
> 所有者的净利润186,930.08 万元，**同比增长48.14%**

**BM25 把这块排第 1。** 表格块的词汇鸿沟是真的，但同一个事实在正文里有冗余表述，
漏掉表并没有伤到答案。"某个块没召回"≠"这题答不出"——这恰好是我在 ④ 里警告的
那个混淆，只不过这次是我自己反过来犯的。

**② 混合检索不是普遍更好，它的优势是"小预算优势"。**

topk=8 时 mix（20/89）确实赢过 bm25（15/89）和 vec（13/89）两路单打，这是 RRF 该有的样子。
但预算一大就不成立了：**topk=48 时纯 BM25 是 42/89，反超 mix 的 35/89**。
逐题看更清楚，`mix` 有明确的退步题——Q9（口径陷阱）BM25 全中 4/4，`mix` 只中 2/4
（缺 `479,640,950.33`、`4.8`）。加了向量不等于更准，只能说在候选池装得下的时候，
BM25 的"关键词精确匹配"对财务表格这种高度结构化的文本其实很够用。

**③ 扇出真正改善的是覆盖面，不是"答对的题数"。**

我原以为扇出能解决全景题，实测要打个折扣：**平均覆盖公司数从 3.6 家/题抬到 7.6 家/题**
（翻倍，这是实打实的），但**「数值全中」的题数没动**——bm25 3/8、mix 2/8、panorama 3/8
（分母 8 = 有数值基准的题，Q6/Q10 无基准）。原因是全景题要求 12 家的数**全**答对，
覆盖到 7.6 家仍然不算"全中"。

不过在**部分覆盖**这一档，扇出在四道全景题上全面领先，这才是它的价值：

| 题 | bm25 | mix | panorama |
|---|---|---|---|
| Q3 营收前 6 家 | 2/7 | 2/7 | **5/7** |
| Q4 归母/营收排名 | 0/6 | 2/6 | **3/6** |
| Q5 营收同比下滑 | 1/5 | 1/5 | **4/5** |
| Q8 归母同比下滑 | 4/10 | 3/10 | **7/10** |

**④ 检索失败会被模型包装成"财报未披露"。** 系统提示词强制弃答（这本身是对的，
能防止模型用常识编数），但检索失败时它就变成一句自信的"未披露"——
**把检索问题伪装成了事实**。所以评测必须记录"召回没召回到"，不能只看答案像不像。
反过来也一样成立：**只看"召回没召回到"就断言"答不出"，同样会错**（见 ①）。

## 7. 复现注意

- **模型下载**：`HF_ENDPOINT=https://hf-mirror.com`，且必须设 `HF_HUB_DISABLE_XET=1`
  ——新版 Xet 协议走的 `cas-server.xethub.hf.co` 镜像不代理，会 401。
- **CUDA torch**：Windows 下 wheel 自带 CUDA DLL，不需要单独的 `nvidia-*` 包。
- **显存**：6.4G 很紧，编码器按 token 预算组批（默认 45000/批），OOM 时自动劈半重试。
- **自研编码器**：`sentence-transformers` 每次 `encode` 调用有一笔很大的固定开销，
  且 padding 浪费到 44%。自研版按长度排序组批，实测与 ST 结果余弦相似度
  **最低 0.9998**，速度快 1.3 倍。
